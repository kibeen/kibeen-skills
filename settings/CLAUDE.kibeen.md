## 스킬 선택
- 코드를 바꾼 구현 PR 은 크기와 관계없이 `pr-review-loop` 로 올린다(draft PR, 리뷰 self-approve, CI). 오래 걸리는 검증이 없으면 평가 단계만 건너뛴다. superpowers 의 `requesting-code-review`, `finishing-a-development-branch` 를 따로 부르지 않는다.
- 리뷰 self-approve 뒤 CI 와 평가를 함께 돌린다. 지금 head 의 self-approve, CI 통과, 평가의 합격 기준 충족이 모두 차면 사용자에게 채택을 묻지 않고 `pr-merge-loop` 로 넘어가 PR 을 열고, 필수 CI 실패와 리뷰어 코멘트를 처리해 머지될 때까지 감시한다. 기준에 못 미치면 머지하지 않고 멈춰 보고한다. 스킬이 멈춰 묻는 지점은 그대로 묻는다: PR 본문에 `머지 전 사용자 확인` 줄이 있을 때(사용자가 머지하지 말라고 했거나 결과를 보고 정하겠다고 한 PR), 프로젝트 규칙이 허락을 요구하는 머지, 리뷰할 사람이 정해지지 않은 남의 저장소. 조건이 차기 전에는 auto-merge 를 켜지 않는다.
- 기술 문서, 설계서, 제안서는 `doc-coauthoring` 을 쓴다.
- 글쓰기 요청에는 superpowers `brainstorming` 을 쓰지 않는다. `brainstorming` 은 소프트웨어 기능 설계에만 쓴다.
- 프로젝트에 같은 일을 하는 전용 스킬이나 에이전트가 있으면 그것을 먼저 쓴다. 다만 구현 PR 의 리뷰 루프는 `pr-review-loop` 가 맡고, 프로젝트의 리뷰와 푸시 전 점검 스킬은 그 안에서 쓴다.

## 보고
- 이 절은 사용자에게 보내는 대화 답변(진행 상황과 결과 보고)에 적용한다. 스킬이나 템플릿이 형식을 정한 글(PR 본문, 리뷰 코멘트, 스킬이 정한 보고)은 그 형식을 따른다.
- 간결함과 맥락은 서로 독립이다. 간결함은 지엽적인 정보를 빼는 일이고, 맥락은 보고를 이해하는 데 필요한 정보를 주는 일이다. 짧게 쓰려고 맥락을 빼지 않고, 맥락을 준다며 지엽적인 정보를 늘어놓지 않는다.
- 결과부터 쓴다: 바뀐 것, 지금 상태, 사용자가 결정하거나 할 일.
- 보고만 읽고 이해할 수 있게 쓴다. 사용자는 도구 출력과 중간 과정을 보지 못했고, 이 세션이 알아낸 사실을 모른다고 가정한다.
  - 사용자가 이 대화에서 아직 보지 못한 이름(도구, 파일, 커밋, 서버, 설정 키, 이슈 번호, 약어)은 처음 나올 때 무엇이고 이 일에서 어떤 역할인지 한마디로 밝힌다. 사용자가 먼저 꺼냈거나 이미 설명한 이름은 다시 설명하지 않는다.
  - 수치와 상태는 기준과 함께 쓴다: 무엇에서 무엇으로 바뀌었는지, 무엇과 비교한 값인지, 단위와 조건.
  - 결과가 사용자에게 무슨 뜻인지(영향, 남은 위험)와 그렇게 판단한 근거를 붙인다.
  - 결정을 물을 때는 왜 사용자가 정해야 하는지와 선택지마다 무엇이 달라지는지 적는다.
  - 예: "플러그인을 1446438 에서 50c915b 로 올렸다" 로 끝내지 않고, 그 커밋이 무엇을 바꿨는지와 사용자에게 미치는 영향(다음 세션부터 적용 등)을 붙인다.
- 지엽적인 정보는 뺀다: 거친 단계와 실행한 명령, 시도했다 버린 방법, 확인했는데 문제없던 항목, 이미 한 말의 반복, 끝맺음 요약. 사용자가 물으면 그때 자세히 답한다.
- 작업 중 진행 보고는 한두 문장으로 지금 하는 일과 막힌 것만 쓴다. 단계마다 보고하지 않는다.
- 서브에이전트나 다른 세션의 결과를 전할 때도 같은 기준으로 줄인다. 원문을 그대로 옮기지 않되, 그 결과를 이해하는 데 필요한 맥락(무엇을 왜 조사했는지)은 붙인다.
- 줄여도 빠뜨리지 않는다: 실패와 오류, 검증하지 못한 부분, 되돌리기 어려운 변경, 사용자 확인이 필요한 일.
