# PR 리뷰 루프

목적: 몇 시간짜리 검증을 돌린 뒤에 코드 리뷰에서 결함이 나와 다시 평가하는 낭비를 막는다.
리뷰와 CI 를 검증보다 **먼저** 끝낸다. 모든 단계의 결과는 PR 코멘트로 남긴다.

모든 코멘트 첫 줄에는 단계 표시를 넣는다. 다음 세션이 이 표시로 진행 상태를 이어받는다.
`<!-- pr-review-loop step=<review|fix|ci|poc|close> round=<N> sha=<head 커밋> -->`

진행 상태 확인: `gh pr view <PR> --comments` 에서 마지막 표시를 찾는다.

## 0. 준비
- `gh auth status` 가 통과하고, 작업 브랜치가 커밋·푸시돼 있어야 한다. 커밋 안 된 변경이 있으면 먼저 커밋한다.
- 이 브랜치에 열린 PR 이 이미 있으면 새로 만들지 않고 그 PR 로 이어간다: `gh pr list --head <브랜치>`.

## 1. draft PR 생성
```bash
gh pr create --draft --base <base> --title "<제목>" --body-file <본문.md>
```
본문에는 아래 네 절을 넣는다. **PoC 평가 계획**이 빠지면 리뷰어가 검증 준비를 볼 수 없다.
- 변경 요약: 무엇을 왜 바꿨는지.
- 테스트: 추가하거나 돌린 테스트.
- PoC 평가 계획: 무엇을, 어떤 설정·데이터로, 어떤 지표로 잴지. 비교 기준(기준선)과 결과를 판단할 기준.
- 진행 상태: `[ ] 리뷰 Approve`, `[ ] CI 통과`, `[ ] PoC 평가`.

## 2~4. 리뷰 루프 (최대 3회)
라운드 N 마다:
1. 서브에이전트 `pr-reviewer` 를 띄운다. 프롬프트에는 저장소, PR 번호, 라운드 N, (N≥2 면) 직전 리뷰 코멘트와
   반영 코멘트 URL 만 준다. 내 결론이나 변명은 덧붙이지 않는다(독립 리뷰가 목적이다).
2. 리뷰어가 PR 에 리뷰 코멘트(step=review)를 올리고 `VERDICT: APPROVE` 또는 `VERDICT: CHANGES_REQUESTED` 를 돌려준다.
   이 판정이 self-approve 다. GitHub PR 의 승인(Approve) 상태는 바꾸지 않는다.
3. `CHANGES_REQUESTED` 면 Must fix 를 하나씩 고치고 커밋·푸시한다. Should fix 는 고치거나, 안 고치는 이유를 적는다.
   그다음 반영 코멘트(step=fix)를 올린다: 항목마다 `고침 → <커밋>` 또는 `안 고침 → <이유>`.
4. 다음 라운드로 간다. 리뷰어는 반영을 하나씩 확인하고 새 diff 를 본다.

- `APPROVE`(self-approve) 면 5단계로 간다.
- 3회 안에 self-approve 가 안 나면 멈춘다. 남은 Must fix 와 쟁점을 사용자에게 보고하고 지시를 기다린다.

## 5~6. CI 루프 (통과할 때까지)
1. 레포의 CI 실행 규칙을 먼저 확인한다(레포 `CLAUDE.md`, 레포 전용 스킬). draft 에서 돌지 않거나 라벨이 필요한 레포는
   그 규칙을 따른다(예: `gh pr ready <PR>` 뒤에 실행 라벨). 규칙이 없으면 푸시로 이미 돌고 있다.
2. 감시: `gh pr checks <PR> --watch --interval 30`. 체크가 하나도 안 붙으면 사용자에게 알린다.
3. 실패하면 로그를 본다: `gh run view <run-id> --log-failed | tail -200`.
   CI 코멘트(step=ci)를 올린다: 실패한 체크, 원인, 고칠 방법. 고치고 커밋·푸시한 뒤 2로 돌아간다.
4. 같은 실패가 세 번 이어지거나, 실패가 이 PR 과 무관해 보이면(인프라, 기존 결함, flaky) 멈추고 사용자에게 보고한다.
5. 모든 체크가 통과하면 7단계로 간다.

## 7. PoC 평가와 보고
1. PR 본문의 PoC 평가 계획대로 평가를 돌린다. 평가 중에 코드를 고치지 않는다. 고쳐야 하면 멈추고 2단계(리뷰)로 돌아간다.
2. 결과 코멘트(step=poc)를 올린다: 평가한 커밋, 조건과 설정, 지표 결과 표, 기준선 대비, 계획의 판단 기준에 비춘 해석.
3. 사용자에게 결과를 짧게 보고하고 판정을 묻는다: **채택 / 폐기 / 추가 평가**. 폐기 여부는 사용자가 정한다.

## 8. 판정 뒤 처리
- **폐기**: 사용자가 폐기라고 하면 묻지 않고 정리한다. GitHub 는 PR 을 삭제할 수 없으므로 닫고 브랜치를 지운다.
  ```bash
  gh pr close <PR> --delete-branch --comment "<!-- pr-review-loop step=close round=1 sha=<head> -->
  폐기: <사유>"
  ```
  브랜치에 남의 커밋이 있거나 다른 PR 이 같은 브랜치를 쓰면(`gh pr list --head <브랜치> --state open`) 브랜치는 지우지 말고
  PR 만 닫는다(`--delete-branch` 빼기). 로컬 워크트리가 있으면 함께 정리한다.
- **채택**: draft 면 `gh pr ready <PR>` 로 바꾸고, 레포의 일반 머지 절차를 따른다.
- **추가 평가**: 7단계로 돌아간다. 코드를 바꾸면 2단계부터 다시 한다.
