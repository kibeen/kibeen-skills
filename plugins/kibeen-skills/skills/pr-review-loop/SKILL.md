# PR 리뷰 루프

목적: 구현 PR 을 독립 리뷰와 CI 를 거친 상태로 올린다. 몇 시간짜리 검증이 있는 변경은 그 검증을 돌린 뒤에
코드 리뷰에서 결함이 나와 다시 평가하는 낭비를 막는다. 리뷰를 검증보다 **먼저** 끝내고, CI 는 검증과 **함께** 돌린다.
모든 단계의 결과는 PR 코멘트로 남긴다.

대상은 코드를 바꾼 모든 구현 PR 이다. 단위 테스트로 검증이 끝나는 작은 수정도 같은 절차를 거치고,
PoC 평가(7단계의 1-2)만 건너뛴다. 채택 판정은 똑같이 받는다.

모든 코멘트 첫 줄에는 단계 표시를 넣는다. 다음 세션이 이 표시로 진행 상태를 이어받는다.
`<!-- pr-review-loop step=<review|fix|ci|poc|close> round=<N> sha=<head 커밋> -->`
`round` 는 그 step 의 순번이고(리뷰 라운드, CI 실패 횟수, 평가 코멘트 순번) `sha` 는 코멘트를 올릴 때의 head 다.
평가한 커밋은 head 와 다를 수 있으므로 평가 코멘트의 본문에 적는다.
(`open`, `hold`, `feedback` 표시는 채택 뒤 `pr-merge-loop` 가 쓴다.)

## 진행 상태 확인
새 세션에서 이어받거나 앞의 대화가 줄어들었을 때 `gh pr view <PR> --comments` 로 표시를 읽는다.
`step=open` 이나 `step=hold` 표시가 하나라도 있으면 사용자가 채택한 적이 있는 PR 이다. 스킬 `pr-merge-loop` 의
"상태 읽기와 기록" 대로 이어간다. `pr-merge-loop` 가 재평가 중(`markers.reevaluating`)이라고 돌려보낸 PR 은 아래대로 읽는다.

CI 와 평가가 따로 진행되므로 마지막 표시 하나로 판단하지 않는다. 셋을 따로 읽는다.
- **리뷰**: 마지막 `step=review` 의 VERDICT 와 sha, 라운드 수(상한은 마지막 `사용자 지시 재평가` 무효 뒤의 라운드만 센다).
  평가 계획이 있는 PR 에서 그 뒤에 `동작을 바꾼다` 로 판정된 수정(`CI 수정 →` 반영 코멘트)이 푸시됐으면 그 APPROVE 는
  지금 head 의 것이 아니다. 재리뷰가 먼저다. 계획이 `없음` 이면 CI 수정은 APPROVE 를 무효로 하지 않는다(7단계의 4 에서 바뀐 내용을 보인다).
- **평가**: `step=poc` 코멘트를 시간순으로 본다. 본문 첫 줄이 `평가 시작:`, `평가 결과:`, `평가 중단:`, `평가 무효:` 중 하나다.
  - 마지막이 `평가 시작:` 이면 거기 적힌 트리와 자원에서 프로세스가 살아 있는지 먼저 확인한다. 확인하기 전에 새 평가를
    띄우지 않는다. 살아 있으면 이어받는다. 없으면 결과가 끝까지 나왔는지 본다. 끝났으면 7단계의 2 로 간다. 덜 끝났으면
    "중단하고 다시 재는 순서" 의 1-2 를 하고(횟수에 넣는다) 상한에 걸리지 않았을 때만 다시 시작한다.
  - 마지막이 `평가 중단:` 이나 `평가 무효:` 이면 둘의 수를 센다. 사유가 `사용자 지시 재평가` 인 무효는 세지 않고, 그 코멘트 뒤의
    것만 센다. 두 번 이상이면 사용자 지시 없이 평가를 다시 시작하지 않는다(지시가 대화에 없으면 다시 묻는다).
    한 번 이하면 지금 head 가 self-approve 된 상태일 때(수정이 있었으면 재리뷰 뒤) 다시 시작한다.
  - `평가 결과:` 는 같은 커밋의 `평가 무효:` 가 뒤에 없고, 그 커밋부터 지금 head 까지의 수정이 모두 `step=ci` 코멘트에서
    "동작을 바꾸지 않음" 으로 판정됐을 때만 유효하다. 그 밖의 커밋이 끼어 있으면 `평가 무효:` 를 올리고 다시 잰다.
  - 마지막 결과의 `남은 항목` 이 `없음` 이 아니면 평가가 덜 끝난 것이다.
- **CI**: `gh pr checks <PR>` 의 지금 상태. 감시는 세션과 함께 끝나므로 다시 띄운다. 마지막 `step=ci` 의 판정이
  "동작을 바꾼다" 인데 그 뒤에 `평가 중단:`, `평가 무효:`, `CI 수정 →` 반영 코멘트(step=fix) 중 어느 것도 없으면
  "중단하고 다시 재는 순서" 를 1번부터 한다.

## 0. 준비
- `gh auth status` 가 통과하고, 작업 브랜치가 커밋·푸시돼 있어야 한다. 커밋 안 된 변경이 있으면 먼저 커밋한다.
- 이 브랜치에 열린 PR 이 이미 있으면 새로 만들지 않고 그 PR 로 이어간다: `gh pr list --head <브랜치>`.

## 1. draft PR 생성
```bash
gh pr create --draft --base <base> --title "<제목>" --body-file <본문.md>
```
본문에는 아래 네 절을 넣는다. **PoC 평가 계획**이 빠지면 리뷰어가 검증 준비를 볼 수 없다.
- 변경 요약: 무엇을 왜 바꿨는지.
- 테스트: 추가하거나 돌린 테스트.
- PoC 평가 계획: 무엇을, 어떤 설정·데이터로, 어떤 지표로 잴지. 비교 기준(기준선)과 결과를 판단할 기준.
  CI 통과 뒤에만 돌릴 항목(5~7단계의 기준)은 항목마다 `CI 뒤` 라고 표시한다.
  오래 걸리는 검증이 없는 변경은 `없음` 이라고 적고, 무엇으로 검증했는지와 평가가 필요 없는 이유를 한두 줄로 쓴다.
- 진행 상태: `[ ] 리뷰 self-approve`, `[ ] CI 통과`, `[ ] PoC 평가`. 평가가 없으면 마지막 항목을 `PoC 평가: 없음` 으로 쓴다.
  채택을 묻기 전에 이 목록을 실제 상태로 고친다(`gh pr edit <PR> --body-file`).

## 2~4. 리뷰 루프 (최대 3회)
라운드 N 마다:
1. 서브에이전트 `pr-reviewer` 를 띄운다. 프롬프트에는 저장소, PR 번호, 라운드 N, (N≥2 면) 직전 리뷰 코멘트와
   반영 코멘트 URL 만 준다. 내 결론이나 변명은 덧붙이지 않는다(독립 리뷰가 목적이다).
2. 리뷰어가 PR 에 리뷰 코멘트(step=review)를 올리고 `VERDICT: APPROVE` 또는 `VERDICT: CHANGES_REQUESTED` 를 돌려준다.
   이 판정이 self-approve 다. GitHub PR 의 승인(Approve) 상태는 바꾸지 않는다.
3. `CHANGES_REQUESTED` 면 Must fix 를 하나씩 고치고 커밋·푸시한다. Should fix 는 고치거나, 안 고치는 이유를 적는다.
   그다음 반영 코멘트(step=fix)를 올린다: 항목마다 `고침 → <커밋>` 또는 `안 고침 → <이유>`.
4. 다음 라운드로 간다. 리뷰어는 반영을 하나씩 확인하고 새 diff 를 본다.

- `APPROVE`(self-approve) 면 5단계를 시작하고, 평가 계획이 있으면 7단계의 1 도 함께 시작한다
  (중단·무효 상한에 걸렸고 사용자 지시가 없으면 평가는 시작하지 않는다).
- 3회 안에 self-approve 가 안 나면 멈춘다. 남은 Must fix 와 쟁점을 사용자에게 보고하고 지시를 기다린다.

## 5~7. CI 와 PoC 평가를 함께 진행
self-approve 가 나면 CI 와 PoC 평가를 함께 시작한다. CI 통과를 기다렸다가 평가를 시작하지 않는다.
평가 계획이 `없음` 이면 CI 만 돌린다.

- **CI 통과 뒤에만 시작하는 평가**: 내가 바로 멈추고 되돌릴 수 없는 것(배포, 공유 파이프라인 실행, 다른 사람이나
  다른 에이전트에게 맡기는 실행)과 레포 규칙이 CI 통과를 요구하는 것. 그 항목만 CI 뒤로 미룬다(7단계의 3).
  내가 예약해 쓰고 중단하면 바로 반납할 수 있는 장비에서 도는 벤치마크는 여기에 들지 않는다.
- **평가는 평가 커밋에 고정된 트리에서 돌린다**: `git worktree add --detach <경로> <평가 커밋>` 이나 그 커밋의 빌드 산출물.
  원격에서 도는 평가도 브랜치 이름이 아니라 커밋 해시로 고정한다. CI 수정은 그 트리에서 하지 않는다.
  돌고 있는 평가가 고친 코드를 읽으면 무엇을 쟀는지 알 수 없게 된다.

### 5~6. CI 루프 (통과할 때까지)
1. 레포의 CI 실행 규칙을 먼저 확인한다(레포 `CLAUDE.md`, 레포 전용 스킬). draft 에서 돌지 않거나 라벨이 필요한 레포는
   그 규칙을 따른다(예: `gh pr ready <PR>` 뒤에 실행 라벨). 규칙이 없으면 푸시로 이미 돌고 있다.
   ready 로 바꾸더라도 auto-merge 는 켜지 않는다. 레포 자동화가 켰으면 끈다(`gh pr merge <PR> --disable-auto`).
   auto-merge 는 사용자가 채택한 뒤에만 켠다.
2. 감시: `gh pr checks <PR> --watch --fail-fast --interval 30` 을 백그라운드로 띄운다(Bash 의 `run_in_background`).
   끝나면 하네스가 다시 불러 주므로 평가가 도는 동안 CI 를 폴링하지 않는다. 백그라운드 실행이 없는 환경이면 평가의
   구간 사이에 `gh pr checks <PR>` 로 확인한다. 체크가 하나도 안 붙으면 사용자에게 알린다.
3. 실패하면 로그를 본다: `gh run view <run-id> --log-failed | tail -200`. 평가 계획이 있으면 고치기 **전에** 그 수정이
   평가가 재는 동작을 바꾸는지 판정한다(아래 "CI 수정과 평가"). 평가가 아직 시작 전이어도 판정은 같다.
   CI 코멘트(step=ci)를 올린다: 실패한 체크, 원인, 고칠 방법, 판정(`동작을 바꾸지 않음` 또는 `동작을 바꾼다`).
   - 바꾸지 않는 수정이면 고치고 커밋·푸시한 뒤 이 루프의 2번으로 돌아간다.
   - 바꾸는 수정이면 여기서 고치지 않고 "중단하고 다시 재는 순서" 를 따른다.
   - 평가 계획이 `없음` 이면 판정 없이 고치고 커밋·푸시한 뒤 2번으로 돌아간다.
4. 같은 실패가 세 번 이어지거나, 실패가 이 PR 과 무관해 보이면(인프라, 기존 결함, flaky) CI 코멘트(첫 줄 `CI 수정 중단: <근거>`)를
   올리고 CI 수정을 멈춘 뒤 사용자에게 보고한다. 돌고 있는 평가는 끝까지 돌린다.
5. 모든 체크가 통과하면 7단계의 3 으로 간다.

체크를 통과시키려고 테스트를 skip 하거나 지우거나 기대값을 실패에 맞추지 않는다.

### CI 수정과 평가
| CI 실패를 고치는 수정 | 할 일 |
|---|---|
| 평가가 재는 동작을 바꾸지 않는다(테스트, lint, 타입, 주석과 문서, 이름 변경, 측정 경로 밖의 코드, 측정 경로의 코드가 바뀌지 않는 base merge) | 고쳐서 푸시한다. 평가는 계속 돌리고, 결과는 평가 커밋 기준으로 유효하다 |
| 동작을 바꾼다(알고리즘, 기본값과 설정, 측정 경로의 분기) | 평가를 **즉시 중단**하고 다시 잰다(아래 순서) |
| 어느 쪽인지 애매하다 | 바꾸는 쪽으로 본다 |

테스트가 잡은 것이 측정 경로의 결함이면 그 수정은 동작을 바꾸는 수정이다. 평가를 살리려고 판정을 유리하게 내리지 않는다.
바꾸지 않는다고 판정한 수정도 푸시하기 전에 `git diff --stat <평가 커밋>..` 로 다시 확인한다(평가 시작 전이면 self-approve 된 커밋 기준).

중단하고 다시 재는 순서(평가를 시작하기 전이면 1-2 는 건너뛰고 횟수에도 넣지 않는다):
1. 평가가 띄운 것을 모두 멈춘다(서빙, 부하 생성기, 평가를 맡긴 서브에이전트와 백그라운드 작업). 남은 프로세스가 없는지
   확인한 뒤 공유 자원(장비 예약 등)을 레포 규칙대로 반납한다. 부분 결과는 지우지 않되 쓰지 않는다.
   바뀌지 않은 기준선(base 커밋)의 끝난 측정은 다시 써도 된다.
2. 중단 코멘트(step=poc)를 올린다: `평가 중단: 커밋 <평가 커밋>, <사유>. 부분 결과는 무효.`
   결과를 이미 사용자에게 알렸으면 무효가 된 사실과 사유를 바로 알린다.
3. 고치고 커밋·푸시한 뒤 반영 코멘트(step=fix)에 `CI 수정 → <커밋>` 을 적어 올리고 2단계(리뷰)로 돌아간다.
   리뷰어에게는 직전 리뷰 코멘트와 이 반영 코멘트의 URL 을 준다. 라운드는 이어서 세고 상한 3회도 그대로다.
   남은 라운드가 없으면 리뷰를 띄우지 않고 멈춘다. 중단한 평가, 푸시한 수정, 리뷰가 필요한 이유를 사용자에게 보고하고
   지시를 기다린다. 이전 APPROVE 는 이 커밋에 해당하지 않는다.
4. self-approve 가 나면 새 커밋으로 평가를 새 출력 경로에서 다시 시작한다. CI 는 푸시로 이미 돌고 있으면 그대로 감시한다.

평가가 이미 끝난 뒤에 동작을 바꾸는 수정이 필요해져도 같은 순서다. 2번의 코멘트는 `평가 무효: 커밋 <평가 커밋>, <사유>.` 로 쓴다.
평가가 스스로 죽은 경우(장비, 인프라)도 `평가 중단:` 으로 기록하고 횟수에 넣는다.
중단이나 무효는 두 번째부터 2번까지 하고 바로 사용자에게 보고한다. 수정과 재리뷰, CI 는 계속하되 평가는 사용자 지시가
있을 때만 다시 시작한다.

### 7. PoC 평가와 채택 판정
1. PR 본문의 PoC 평가 계획대로 평가를 돌린다(`CI 뒤` 항목은 3에서). 시작할 때의 head 가 평가 커밋이다.
   지금 돌릴 항목이 없으면(전부 `CI 뒤`) 시작 코멘트를 올리지 않는다. 있으면 시작하면서 시작 코멘트(step=poc)를 올린다:
   `평가 시작: 커밋 <평가 커밋>, 트리 <경로나 산출물>, 자원 <장비와 예약>, 지금 돌리는 항목 <...>, CI 뒤로 미룬 항목 <없음 | ...>`
2. 끝나면 프로세스를 정리하고 공유 자원을 반납한다. 그다음 평가 트리의 HEAD 가 평가 커밋인지, 평가를 시작한 뒤에 소스가
   고쳐지지 않았는지 확인한다(`git -C <트리> status --porcelain` 에서 평가가 만든 빌드 산출물, 런타임 설정, 출력 파일은 뺀다).
   HEAD 가 다르거나 소스가 고쳐졌으면 `평가 무효:` 를 올리고 다시 잰다. 아니면 결과 코멘트(step=poc)를 올린다:
   `평가 결과: 커밋 <평가 커밋>, 항목 <이번에 잰 것>, 남은 항목 <없음 | ...>` 다음에 조건과 설정, 지표 결과 표,
   기준선 대비, 계획의 판단 기준에 비춘 해석.
3. CI 상태를 본다. 결과는 사용자에게 먼저 알려도 되지만 채택은 아래 조건이 찬 뒤에 묻는다.
   - 돌고 있으면 기다린다.
   - 통과했으면 `CI 뒤` 항목을 CI 를 통과한 head 로 돌리고 1-2 와 같은 코멘트를 남긴다. 레포 규칙이 그 실행에
     사용자 확인을 요구하면 받는다.
   - 실패한 채 멈췄으면(5~6 의 4) `CI 뒤` 항목을 시작하지 않고 채택도 묻지 않는다. 평가 결과와 CI 상태를 보고하고
     CI 를 어떻게 할지 지시를 기다린다.
4. CI 가 통과했고 `남은 항목` 이 `없음` 인 유효한 평가 결과가 있을 때(계획이 `없음` 이면 CI 가 통과했을 때) 사용자에게 결과를 공유하고
   채택 여부를 묻는다: **채택 / 폐기 / 추가 평가**.
   공유할 것: 지표 결과와 기준선 대비 차이, 판단 기준을 넘었는지, 평가한 커밋, PR 과 결과 코멘트 링크, 리뷰와 CI 상태.
   평가한 커밋(평가가 없으면 self-approve 된 커밋)과 지금 head 가 다르면 그 사이에 바뀐 파일
   (`git diff --stat <그 커밋>..HEAD`)과, 동작이 바뀌었는지와 그렇게 본 근거도 보인다.
5. 답을 기다린다. 결과가 기준을 넘어도 채택은 사용자가 정하고, 무응답은 채택이 아니다.
   답이 오기 전에는 auto-merge 를 켜지 않고 머지하지 않는다. draft 인 PR 은 draft 로 둔다.

PoC 평가 계획이 `없음` 이면 1-2 를 건너뛴다. 4 에서 리뷰와 CI 결과, 무엇으로 검증했는지를 공유하고 **채택 / 폐기** 를 묻는다.

## 8. 판정 뒤 처리
돌고 있는 평가가 있으면 어느 판정이든 먼저 "중단하고 다시 재는 순서" 의 1-2 를 한다(프로세스 정리, 자원 반납, 평가 중단 코멘트).
- **폐기**: 사용자가 폐기라고 하면 묻지 않고 정리한다. GitHub 는 PR 을 삭제할 수 없으므로 닫고 브랜치를 지운다.
  ```bash
  gh pr close <PR> --delete-branch --comment "<!-- pr-review-loop step=close round=1 sha=<head> -->
  폐기: <사유>"
  ```
  브랜치에 남의 커밋이 있거나 다른 PR 이 같은 브랜치를 쓰면(`gh pr list --head <브랜치> --state open`) 브랜치는 지우지 말고
  PR 만 닫는다(`--delete-branch` 빼기). 로컬 워크트리가 있으면 함께 정리한다.
- **채택**: 스킬 `pr-merge-loop` 로 넘어간다. PR 열기, auto-merge, 머지를 막는 CI 실패 수정, 리뷰어 코멘트 반영을 거쳐
  PR 이 머지될 때까지 그 절차가 맡는다.
- **추가 평가**: 7단계로 돌아간다. 코드를 바꾸면 먼저 `평가 무효: 커밋 <옛 평가 커밋>, 사용자 지시 재평가.` 를 올리고 2단계부터 다시 한다.
  사용자가 지시한 재평가는 리뷰 라운드 상한을 새로 3회 받는다(`round` 번호는 이어서 센다).
